# PARTS GATE セキュリティ・企業間データ分離設計

- 版: 0.1（STEP 3 設計・ドラフト）／作成日: 2026-11-05

## 1. 最重要: 企業間のデータ分離

### 1-1. 守ること

1. company_id は**ログイン情報（`/auth/me` の company_id）からだけ**決める。URL・本文・ヘッダーの company_id は読まない
2. すべての SQL に `company_id = ?` を付ける。**手書きせず、共通のスコープ関数を通す**（HaLSpace では手書きの WHERE で会社スコープが漏れた前例がある）
3. 他社の ID を指定されたら 404（403 にしない。存在を知らせない）
4. 会社をまたぐ参照を DB でも防ぐ: 明細 → 伝票・置場・納品先、読み取り → 明細・作業セッションは、`(company_id, id)` の組で参照する
5. R2 のキーは `imports/<company_id>/…`、`backups/<company_id>/…`。ファイルの配信は必ず DB の取込回（会社で絞り済み）から R2 キーを引く。画面から R2 キーを受け取らない
6. 集計表・監査ログ・設定も会社ごと

### 1-2. 実装の形

```ts
// db/scope.ts（例）: ハンドラは c.get('companyId') を直接 SQL に書かない
export function scoped(c: Ctx) {
  const companyId = c.get('companyId'); // 認証ミドルウェアだけが設定する
  return {
    first: <T>(sql: string, ...args: unknown[]) => c.env.DB.prepare(assertScoped(sql)).bind(companyId, ...args).first<T>(),
    // all / run / batch も同様
  };
}
// assertScoped: SQL に "company_id = ?1" が含まれなければ例外（テストで全 SQL を検査）
```

### 1-3. テナント分離テスト（必須。STEP 8 だけでなく各 STEP で追加する）

- テスト用に会社 A・会社 B を作り、それぞれにユーザー・担当者・置場・納品先・注文・読み取り履歴・取込回を入れる
- **全 API について**、A のトークンで B の ID を指定 → 404、一覧に B のデータが 0 件、更新・削除が効かないことを確認する（API 一覧からテストを自動生成し、API を足したのにテストがない場合は失敗させる）
- 本文に `company_id: B` を入れても A のデータとして扱われる（または無視される）こと
- A のバーコードを B の作業セッションで読む → 未登録
- A の取込回のファイルを B から取得 → 404
- SQL 検査: ソース中の全 SQL に company_id の条件があること（`assertScoped` の単体テスト）

## 2. 認証・セッション

| 項目 | 方針 |
| --- | --- |
| ログイン | Space.app（halspace-api）。パスワードのハッシュ化・2 段階認証（メール OTP）・ログイン回数制限は Space.app 側で実装済み |
| トークン | sessionStorage の `space_token`（タブごとに独立。localStorage に置かない） |
| 検証 | partsgate-api が `/auth/me` で確認し、60 秒キャッシュ（トークンの SHA-256 をキーにし、トークン本体は持たない） |
| セッション期限 | Space.app のトークンは無期限のため、PARTS GATE 側で「最後の操作から 12 時間（設定可）で再ログイン」を画面と API の両方で行う |
| ログアウト | 画面のログアウトで作業セッションを終了し、sessionStorage を消す。Space.app から入った場合は「アプリ選択に戻る」（Space.app 共通の決まり） |
| 作業担当者 | 作業セッションは画面のメモリだけに持つ。API で毎回、利用者・会社・終了していないかを確認 |
| CSRF | Cookie を使わず Bearer 方式なので対象外。CORS は許可オリジンのみ |

## 4. 入力・出力

- SQL はすべて prepared statement＋`bind()`。文字列をつなげて SQL を作らない（並び替えの列名などは許可リストから選ぶ）
- 入力は API で型・長さ・形式を確認（画面の確認は補助）
- XSS: React の通常の表示だけを使う。`dangerouslySetInnerHTML` 禁止。CSV 由来の文字列もそのまま文字として表示
- CSV 出力: BOM 付き UTF-8・CRLF。`= + - @` で始まるセルは先頭に `'` を付ける（Excel の数式実行を防ぐ）
- アップロード: `.csv`・10MB 以下・NUL 文字なし（[csv-import.md](csv-import.md) §2）。R2 は非公開、配信は API 経由

## 5. 監査ログに残す操作

CSV 取込の確定、担当者・置場・納品先・設定の変更、ユーザーのロール・状態の変更、読み取りの取消、要確認の解決、CSV 出力、企業情報の変更、バックアップからの復元。

## 6. 秘密情報

- ローカルは `api/.dev.vars`（Git 管理外）。本番は `wrangler secret put`
- `wrangler.toml` には名前と D1/R2 の ID だけを書く
- テストはダミーデータのみ。ヒラノの実データ（得意先名など）をリポジトリに入れない。サンプル CSV もコミットしない（`.gitignore`）
