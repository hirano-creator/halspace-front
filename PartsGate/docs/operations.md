# PARTS GATE 運用マニュアル

読む人: PARTS GATE を運用する人（HaLSpace の運営者・利用会社の管理者）。現場の作業者向けの操作説明ではない。
本番: 画面 `https://space-apps.pages.dev/PartsGate/app/`、API `https://partsgate-api.space-app.workers.dev`、D1 `partsgate-db`、R2 `partsgate-files`（Cloudflare アカウントは h.hirano@hirano50.com）。

## 1. 利用を始める（会社ごとに 1 回）

1. Space.app の管理画面で、会社の利用アプリに PARTS GATE を入れる
2. 使う人ごとに PARTS GATE を有効にする（会社に入れただけでは個人のアプリ一覧に出ない）
3. その会社で最初に開いた **Space.app の管理者** が PARTS GATE の管理者になる。ほかの人は「一般」で登録される。管理者に変えるのは PARTS GATE の「ユーザー」画面から
4. 管理者がマスターを登録する
   - 置場: CSV と同じ書き方で登録する（ヒラノは 4 桁 `0053` など）。登録していない置場の行は取り込むと「要確認」になる
   - 担当者: 読み取りをする人。読み取り画面で最初に選ぶ
5. 読み取り用の PC で PARTS GATE を開き、担当者を選んで、テスト用に 1 枚読んでみる。読み取り用のアカウントは会社で 1 つを複数の PC で使ってよい（担当者の選択は PC ごと。記録には担当者名が残る）

| ロール | できること |
| --- | --- |
| 一般 | 読み取り、注文データ・読み取り履歴・ダッシュボードを見る |
| 管理者 | 一般の操作に加えて、CSV 取込、マスターの登録、読み取りの取消、分析、CSV 出力、監査ログ、設定、ユーザーのロール変更 |

## 2. 毎日の流れ

1. **CSV 取込（管理者）**: その日に届いた注文 CSV を「取込」から入れる。確認画面で、新規・変更・変更なし・エラー・要確認の件数を見てから確定する。同じ CSV を入れ直しても読み取り履歴は変わらない
2. **読み取り（一般）**: 担当者を選び、メーカー納期と置場を選んで、部品のラベルを読む
3. **確認**: 一覧の照合待ちが 0 になったかを見る。結果が「要確認」「未登録」「数量超過」のものは管理者が確かめる

読み取りの結果と音:

| 表示 | 意味 | 音 |
| --- | --- | --- |
| 正常 | 注文の行と一致し、照合済みにした | 正常の音 |
| 読み取り済み | その行は誰かがすでに読んでいる（誰がいつ読んだかが出る） | 注意の音 |
| 要確認 | 注文にはあるが確かめる必要がある（画面で選んでいるメーカー納期と違う日の部品など）。照合済みにはならない | 注意の音 |
| 未登録 | 注文データにない番号 | エラーの音 |
| 数量超過 | 必要な回数より多く読んだ | エラーの音 |

まちがって読んだ記録は、管理者が「読み取り履歴」から取り消す（理由が必要）。元の記録は消さずに「取消」の記録を足す。

## 3. 困ったとき

| 起きたこと | まず確かめること・対応 |
| --- | --- |
| 読んだのに「未登録」になる | ①読んだのが照合用のバーコードか（ラベルには別の番号のバーコードも並んでいる）②その日の CSV を取り込んだか ③読み取り PC の日本語入力がオンでも読めるように直してあるが、念のためオフにする。④運営者は読み取り履歴（scan_logs）にその番号の記録があるかを見る。記録がなければ、読み取りが画面まで届いていない |
| 画面に「通信を再試行中」と出る | 2 秒・5 秒・10 秒あとに自動で送り直す。それでも届かないと「保存されていない可能性があります」と出るので、通信が戻ってからもう一度読む（同じ読み取りを二重に数えることはない） |
| 「送信待ちがいっぱいです」と出る | 通信が切れたまま 20 件たまった。通信が戻るのを待つ |
| 担当者を選ぶ画面に戻された | 担当者の選択が切れた。選び直して読み直す |
| 「要確認」が続く | 画面右上で選んでいるメーカー納期が、読んでいる部品の日と合っているかを見る。翌日分を先に準備するときは、その日を選ぶ |
| しばらくぶりに開いたらログインを求められた | 会社の設定の時間（既定 12 時間）ごとに、もう一度ログインしてもらう作り |
| ログインできない・すぐ切れる | Space.app 自体にログインできるかを見る（PARTS GATE のログインは Space.app のアカウントを使う）。Space.app のアプリ一覧に PARTS GATE が出ないときは、会社と本人の両方で有効になっているかを見る |
| Space.app（halspace-api）が止まっている | ログイン確認の結果は 60 秒だけ覚えているので、短い停止なら作業は続く。長く止まったときは、紙の出荷リストに手で印を付けて確認し、復旧後に読み直す（同じ行を読み直すと「読み取り済み」になるだけで、二重には数えない） |
| 画面が「Something went wrong」になる | 画面の公開（main への反映）の直後、数十秒だけ出ることがある。少し待って再読み込みする |

## 4. 定期の確認（運営者）

| いつ | やること | 方法 |
| --- | --- | --- |
| 自動（毎日 3 時） | 差分バックアップ | Cron が R2 の `backups/<日付>/` に書く。結果は D1 の `backup_runs`（status が `done` か） |
| 月 1 回 | バックアップが毎日できているか | `npx wrangler d1 execute partsgate-db --env production --remote --command "SELECT kind, status, error, created_at FROM backup_runs ORDER BY id DESC LIMIT 35"` |
| 月 1 回 | 全体バックアップ | `npx wrangler d1 export partsgate-db --remote --env production --output full-YYYYMM.sql`。R2 と手元の両方に保存する |
| 月 1 回 | D1 の読み取り行数（無料は 1 日 500 万行で、**アカウント全体で共有**） | `npx wrangler d1 info partsgate-db --env production` の `rows_read_24h`。Cloudflare のダッシュボードで TENQ など同じアカウントの D1 も合わせて見る。数十万行を超えていたら、`wrangler d1 insights partsgate-db --env production --sort-by reads` で多い SQL を探す |
| 月 1 回 | DB の容量（無料は 1 つ 500MB） | 同じ `d1 info` の `database_size`。400MB を超えたら、古い年度の移し方か有料化をオーナーと決める |

Cloudflare を操作する前に、必ず `npx wrangler whoami` で h.hirano@hirano50.com になっていることを確かめる（別のアカウントに戻っていることが多い）。

## 5. 復元

手順は [README](../README.md) の「バックアップと復元」。直近 7 日以内の誤操作は D1 Time Travel、それより前は全体バックアップ → 差分の順に戻す。**本番に流すのはオーナーの承認後**。流す先の DB は必ず人が確かめる。

## 6. 本番への反映（運営者）

- API: `api/` で `npx wrangler deploy --env production`（オーナーの承認後）。表を変えるときは先に `npx wrangler d1 migrations apply partsgate-db --env production --remote`
- 画面: `npm run build`（`web/.env.production` の本番 API でビルドされ、`PartsGate/app/` に出る）→ コミット → main から作った worktree に cherry-pick して push。Pages は main だけを公開する。**feat/cloudflare-migration は TimeCalc の本番反映ブランチなので push しない**
- 反映できたかは HTTP 200 ではなく、公開されたファイルの中身（変えた文字列）で確かめる
