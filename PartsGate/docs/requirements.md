# PARTS GATE 要件と確定事項

- 版: 0.1（STEP 3 設計・ドラフト）／作成日: 2026-11-05
- 元資料: 「PARTS GATE｜最終開発指示書」（以下「指示書」）
- 未確定事項は §6 の番号（Q-n）で参照する

## 1. 目的

注文 CSV と実際の部品をバーコードで照合し、取り違え・数量違い・出荷漏れを防ぐ。誰がいつ何を確認したかを記録し、後から分析できるようにする。最初の導入先は株式会社ヒラノ。最初から複数の会社で使える作りにする。

## 2. 前提として決まったこと（2026-11-05）

| 項目 | 決定内容 | 根拠 |
| --- | --- | --- |
| 載せる場所 | **Space.app のアプリ**として作る。画面は `space-apps.pages.dev/PartsGate/app/` | オーナー判断。ログイン・会社・利用者は Space.app のものを使う |
| 構成 | **Cloudflare Workers＋D1＋R2**（TENQ と同じ方式）。Railway は増やさない | [architecture.md](architecture.md) §2 |
| 費用 | **無料プランで運用する**。Cloudflare は Space.app・TENQ と同じ h.hirano@hirano50.com のアカウント（2026-11-07 決定。使用量を確認し、枠の数%で収まる見込み） | [architecture.md](architecture.md) §6 |
| ラベル | **CSV の 1 行につき 1 枚**。1 回読めばその行は照合完了 | オーナー回答 |
| 置場コード | **CSV と同じ 4 桁**（0053 など）で登録する | オーナー回答 |
| CSV の頻度 | **1 日 1 回**届く | オーナー回答 |
| 出荷完了 | **当面は作らない**。照合までを作る（照合完了と出荷完了は別の状態として DB に場所だけ用意する） | オーナー回答 |

## 3. 実際の CSV から分かったこと

サンプル: `shippinfinst_MJP6993_20261104101909.csv`（ミスミから届く出荷指示データ。81 列・89 行）

| 項目 | 実データ | 設計への反映 |
| --- | --- | --- |
| 文字コード | Shift-JIS（CP932）。全項目ダブルクォート付き。顧客注文番号に半角カナがある | 取込は Shift-JIS と UTF-8 の両方に対応（[csv-import.md](csv-import.md)） |
| ファイル名 | `shippinfinst_<仕入先現法コード><仕入先コード>_<年月日時分秒>.csv` | 取込履歴にファイル名を残す。同じファイルの二重取込を検出する |
| グローバル番号 | 14 桁の英数字（`5P…` 82 行・`5K…` 4 行・`UP…` 3 行）。**1 行ごとに一意** | 明細の識別キー |
| バーコード用グローバル番号 | **89 行すべてグローバル番号と同じ値** | 照合に使う列は会社ごとの設定にする（既定はバーコード用グローバル番号） |
| 受注伝票番号 | 複数行をまとめる（最大 9 行） | 「伝票（orders）」と「明細（order_items）」の 2 階層 |
| 同じ伝票内の同じ商品 | 同じ伝票に同じ商品コードが 2 行ある例あり。グローバル番号は別 | 商品コードではなくグローバル番号で行を見分ける |
| 数量 | 1〜15。`POQTYperbox` は全行で数量と同じ | 1 行＝1 箱（ラベル 1 枚）。数量は画面に大きく表示して目で確認 |
| 置場 | `0053`（川崎・41 行）、`0055`（稲沢・47 行）、`0056`（兵庫 川西・1 行） | 置場マスターと照合。初期データは指示書の表を 4 桁にしたもの（§6 Q-2） |
| お届け先名 | **空欄** | 納品先は「直送先コード＋直送先名」を使う |
| 直送先コード | `S00001` が別々の得意先で使われている | 納品先は **得意先コード＋直送先コード** で見分ける |
| 商品名 | 日本語名は空欄。英語名は `MEVIY SHEET METAL` / `MEVIY SHEET METAL WELDING` の 2 種類 | 一覧は商品コードを主に表示 |
| 日付 | メーカー出荷日（SSD）・ミスミ納期（VRD）は `YYYYMMDD`。サンプルは全行同じ日 | `YYYY-MM-DD` に変換して保存 |
| 輸出区分 | `D`（国内）86 行、`E`（MISUMI USA 向け）3 行 | 一覧・読み取り画面で区別して表示（§6 Q-3） |
| データ区分 | 全行 `F` | `F` 以外が来たら「要確認」にする（意味が分かるまで取り込まない） |

## 4. 指示書から変わる点（Space.app に載せるため）

| 指示書 | PARTS GATE での扱い | 理由 |
| --- | --- | --- |
| §6 ログイン ID・パスワード・最終ログイン | **Space.app のアカウントを使う**。PARTS GATE 側ではアカウントを作らない | ログイン・2 段階認証・停止を Space.app と共通にする。パスワードハッシュは無料プランの CPU 上限（10ms）も超えやすい |
| §6 権限（管理者／一般） | PARTS GATE 内のロールとして D1 に持つ（Space.app の管理者は初回に PARTS GATE 管理者になる） | 会社の管理者と PARTS GATE の管理者を分けられるようにする |
| §8 企業管理 | 会社そのものは Space.app で作る。PARTS GATE の企業管理画面は「PARTS GATE を使う会社の一覧・状態・設定」 | 会社を二重に管理しない |
| §2 公開は Workers Static Assets | 画面は **Space.app と同じ Pages（space-apps.pages.dev）** から配信 | 同じオリジンならログインを引き継げる（別オリジンにすると SSO の仕組みが要る） |
| §2 CSS は Tailwind | そのまま Tailwind（ビルド時だけ使うので本番の容量に影響しない） | 指示書どおり |
| §5 照合結果「数量超過」 | ラベル 1 行 1 枚なので、2 回目の読み取りは「重複」。数量超過は 1 行に複数ラベルを使う会社のための設定として残す | §2 の回答 |
| §3 出荷完了 | 当面作らない | §2 の回答 |

## 5. 照合結果の種類

| 結果 | 表示 | 色 | 条件 |
| --- | --- | --- | --- |
| 正常 | ✔ 正常 | 緑 | 照合待ちの明細と一致した |
| 未登録 | ✖ 未登録 | 赤 | 読んだ番号の明細がない |
| 重複 | ⚠ 読み取り済み | 黄 | すでに照合済みの明細をもう一度読んだ |
| 数量超過 | ✖ 数量超過 | 赤 | 必要枚数（既定 1）を超えた。1 行複数ラベルの会社だけで起きる |
| 要確認 | ⚠ 要確認 | 黄 | 明細はあるが、取消・置場未登録・出荷日が今日でない など（§6 Q-6） |
| エラー | ✖ エラー | 赤 | 通信・サーバーの異常。**読み取りは記録されていない可能性がある**と表示し、再読み取りを促す |
