# TENQ 要件定義書

TENQ — Smart Inspection System（読み: テンク）
QRコード式 工場設備日常点検システム。Space.app のアプリの1つとして提供する。

- 版: 0.1（第1段階・ドラフト）
- 作成日: 2026-10-22
- 状態: **要確認事項（§10）が未確定**。確定した項目から順に版を上げる

---

## 1. 目的

紙で運用している工場設備の日常点検をスマートフォンで行えるようにし、次を実現する。

1. 点検漏れの防止（未点検設備がその日のうちに分かる）
2. 異常の早期発見と、是正・再確認・承認までの追跡
3. 記録管理の効率化（転記・ファイリング・検索の手間をなくす）
4. ISO 監査で求められる記録の保存（作成者・日時・訂正履歴・基準の版）

TENQ は記録の信頼性を支える道具であり、**ISO 適合をシステム単体で保証するものではない**。適用規格・社内手順・保存期間・承認方法は品質管理担当者が確認する（§9）。

## 2. 利用条件

| 項目 | 内容 |
| --- | --- |
| 対象工場 | 複数工場（会社ごと・工場ごとにデータを分ける） |
| 対象設備数 | 30〜100台（1社あたり。設計上は 1,000 台まで性能を落とさない） |
| 利用者 | 一般社員、設備担当者、工場長、システム管理者 |
| 端末 | 社員個人のスマートフォン（BYOD）、PC |
| 通信 | 工場内 Wi-Fi あり（オフライン点検は初期スコープ外。§10 Q-9） |
| 提供形態 | スマートフォンのブラウザで動くレスポンシブ Web アプリ。アプリのインストールは不要（ホーム画面追加は任意） |
| 位置づけ | Space.app のアプリ（SOLID・What'sNo と同列）。ログインアカウントは Space.app と共通 |

## 3. 利用者と権限

### 3-1. ロール

Space.app のサイト権限（`role` = super_admin / admin / general）とは**別に**、TENQ 内のロールを持つ。SOLID の `solid_type` と同じ考え方で、両者を混同しない。

| TENQ ロール | 内部キー | 主な仕事 |
| --- | --- | --- |
| 一般社員 | `worker` | 点検の実施、自分が関わる点検記録の確認、異常報告 |
| 設備担当者 | `equipment_staff` | 担当設備の管理、異常対応、修理状況の更新、点検記録の訂正 |
| 工場長 | `factory_manager` | 工場全体の点検状況・異常対応状況の確認、是正の承認 |
| システム管理者 | `system_admin` | ユーザーの TENQ ロール・所属工場、工場、設備、点検基準、システム設定の管理 |

- ロールは会社内で1つ。所属工場（複数可）は別に持つ。system_admin は自社の全工場が対象
- アカウント自体（作成・パスワード・停止）は Space.app 管理画面で行う。TENQ では「TENQ を使えるか（契約アプリ `tenq`）」「TENQ ロール」「所属工場」「TENQ 内の利用停止」を扱う

確定時の判断（要確認①〜④はすべておすすめを採用）:

1. 異常の承認は**工場長だけ**（システム管理者は承認しない）
2. 一般社員も**同じ工場の他の人の点検記録を見られる**（申し送りのため）
3. 完了した点検記録を直せるのは**設備担当者（担当設備のみ）・工場長・システム管理者**。一般社員は担当者に頼む
4. 一般社員も**工場全体のカード一覧を見られる**

補足:

- 「所属工場」は `user_factories` に登録された工場。system_admin は自社の全工場
- 「担当設備」は `equipment.manager_user_id` が本人の設備
- 再確認は「その異常の是正処置（corrective_actions）を記録した人」以外であることを API で確認する
- 工場長が承認できない期間（長期不在など）の代行は、別の工場長ロールの人を所属工場に追加して対応する（承認権限の一時付与機能は作らない）

**全ての権限判定は API 側で行う**。画面の出し分けは補助であり、API を直接叩いても権限外の操作はできないこと。

## 4. 機能要件

### F-1 ログイン・権限

- Space.app のアカウント（メール＋パスワード、2段階認証）でログインする。TENQ 専用のログイン画面を持つ（Space.app 経由でなくても入れる）
- ログイン後、契約アプリ `tenq` と TENQ ロールを確認する。未割り当てならロール未設定の案内を出す
- **QRコードを読んだだけでは記録を見られない・変えられない**。未ログインで QR を読んだ場合はログイン画面へ送り、ログイン後に該当設備へ戻す
- TENQ 内で利用停止にされたユーザーは即座に API が拒否する
- **スマホではログインを記憶する（2026-10-22 決定）**。ログイン画面の「この端末にログインを記憶する」（スマホでは既定 ON、PC では既定 OFF）を選ぶと、30 日間はログインなしで QR から点検表が開く。記憶は端末ごとに管理し、管理者が端末単位・ユーザー単位で取り消せる（security.md §2-1）

### F-2 工場

- 工場の追加・編集・無効化（コード・名称・所在地・稼働曜日）
- 全データは「会社 → 工場」の範囲で分離する

### F-3 設備台帳

登録項目: 設備ID（システム固定・不変）、設備番号、設備名、工場、設置場所、設備分類、メーカー、型式、管理担当者、使用状態、点検頻度、点検基準（点検項目・判定基準）、備考、QRコード、登録日時・更新日時（作成者・更新者も保存）

- 追加・編集・停止・廃止。物理削除はしない（廃止は状態として残す）
- 設備ID は内部の固定IDで、設備名・設備番号を変えても過去の点検記録との関連は切れない
- 使用状態: `active`（稼働）/ `stopped`（停止中：点検対象外・異常による停止を含む）/ `retired`（廃止）
- 点検頻度: 初期は `daily`（稼働日ごと）/ `weekly` / `monthly`
- 編集はすべて監査ログに前後の値を残す

### F-4 QRコード発行

- 個別発行・一括発行、設備名・設備番号付きラベル、A4 への複数面付け（面付け数は選択）、再印刷
- QR の中身は「TENQ の URL＋ランダムな QR トークン」のみ。パスワード・秘密情報・設備の詳細は含めない
- 再発行（紛失・汚損・張り替え）すると新しいトークンになり、旧トークンは無効化される。旧 QR を読むと「このQRは再発行済み」と案内する。点検記録は設備IDに紐づくため、再発行しても過去の記録は参照できる
- 印刷はブラウザの印刷機能（A4、余白・面付けを CSS で制御）

### F-5 日常点検

- QR を読むと該当設備の点検画面が開く。アプリ内の「QR読み取り」からも開ける（§10 Q-3）
- 点検項目ごとに「正常」「異常」「対象外（許可された項目のみ）」を選ぶ。項目ごとにコメント可
- 必須項目が未選択なら完了できない（画面とAPIの両方で検証）
- 「異常」を選んだ項目は、その場で異常報告へ進める（後からでも可）
- 状態: 未点検（その期間に記録なし）→ 点検中（開始済み・未完了）→ 完了。取消は理由付きの `voided`
- 二重登録防止:
  - 同じ設備・同じ点検期間（例: 2026-10-22）に有効な点検は1件だけ（DBの一意制約で保証）
  - 完了ボタンの連打・通信再送は冪等キーで1件にまとめる
  - 他の人が点検中の設備を開いた場合は「◯◯さんが点検中」と表示し、続行するかを選ばせる（引き継ぎは記録に残す）
- 保存内容: 設備ID、点検日（工場のタイムゾーン基準）、点検者、各項目の判定、コメント、開始・完了日時、点検基準の版、関連する異常報告
- 停止中・廃止の設備は未点検に数えない

### F-6 異常報告・是正処置

記録項目: 異常内容、発見日時、報告者、写真（複数）、危険度、応急処置、対応担当者、対応期限、修理・是正内容、対応完了日、再確認者、承認状況

状態（解釈案。§10 Q-5 で確定）:

| 状態 | キー | 意味 | 次へ進める人 |
| --- | --- | --- | --- |
| 発生 | `reported` | 報告された直後。担当者未定 | 設備担当・工場長 |
| 未対応 | `assigned` | 担当者・期限が決まり、着手前 | 担当者 |
| 対応中 | `in_progress` | 修理・是正の作業中 | 担当者 |
| 是正完了 | `corrected` | 是正内容と完了日を入力済み | 再確認者 |
| 再確認 | `verified` | 是正実施者以外が効果を確認済み（不合格なら対応中へ戻す） | 工場長 |
| 承認・完了 | `closed` | 工場長が承認して完了 | — |

- 状態遷移はすべて履歴（誰が・いつ・コメント）に残し、発生から完了まで追跡できる
- 危険度: 低 / 中 / 高（§10 Q-6）。「高」を選ぶと、設備の使用停止と責任者への連絡を促すメッセージを出し、「設備を停止中にする」操作をその場で選べるようにする。**実際の安全判断は会社の安全管理ルールに従う**旨を画面に明記する
- 未対応（reported/assigned）の異常と、対応期限超過を管理画面で一覧できる
- 写真: JPEG / PNG / WebP、1枚あたり上限 10MB（端末側で長辺 2048px 程度に縮小してから送信）、1件あたり最大 10 枚（設定で変更可）

### F-7 ダッシュボード

- 当日の点検対象設備数・点検完了数・未点検数・異常件数・未対応異常数・期限超過件数
- 設備別の点検履歴、点検者別の実施状況、工場別・設備分類別の集計
- スマートフォンでは数字カード＋未点検リストを優先表示
- **PC は「エリア別の設備カード一覧」を主画面にする（2026-10-22 決定・モック C 案）**。工場の棟・ラインごとの枠に設備カードを並べ、カードを状態の色で塗り分ける。現場の PC・モニターでも一目で分かること
  - 状態と色: 遅れ（期限を過ぎた未点検）＝橙、異常あり＝赤、点検中＝青、未点検＝白地に点線枠、完了・正常＝緑、停止中＝斜線。**色だけでなくアイコンと文字も必ず併記**する
  - エリアごとに「完了台数 / 対象台数」と進み具合のバーを出す
  - 状態で絞り込める。カードを押すと設備の詳細（今日の結果・QR ラベル・点検表・履歴・異常報告）を開く
  - 自動更新（30 秒ごと。点検が完了するとカードの色が変わる）
- 集計の表（点検者別・分類別など）はダッシュボードの下段、または検索画面で見る

### F-12 エリア配置（あとから作る・変える）

カード一覧の「枠（エリア）」と「並び」は、運用を始めてから管理画面で作り・変えられるようにする。コードの修正は不要。

- エリアの作成・名前変更・並べ替え・無効化（例: 「A棟 プレスライン」「屋外」）
- エリアの大きさ（横幅を何列分にするか）と、画面上の位置（行・列）の指定。ドラッグで動かせる
- 設備をエリアに割り当てる（設備台帳の「設置場所」とは別に、画面上の置き場所として持つ）。エリア内のカードの並び順もドラッグで変えられる
- エリア未割り当ての設備は「未配置」の枠に自動で入る（設備を登録した直後でもカード一覧から消えない）
- 配置の変更は工場長・システム管理者。変更は監査ログに残す
- 工場ごとに別の配置を持つ
- Phase 2 候補: 工場の配置図（画像）を背景に置き、その上にカードを置く方式

### F-8 検索・出力

- 検索条件: 期間、工場、設備、点検者、点検結果、異常の有無、対応状況
- 一覧はすべてページネーション（既定 50 件）
- 出力: 点検記録 CSV、設備台帳 CSV、異常・是正処置 CSV、点検記録の印刷用帳票、ISO 監査向けの期間指定記録一覧（訂正履歴・基準の版を含む）
- 出力は権限のある人だけ。出力操作自体を監査ログに残す
- CSV は UTF-8（BOM 付き）・CRLF。Excel の数式実行を防ぐため、`= + - @ タブ CR` で始まるセルは先頭に `'` を付ける

### F-9 点検基準・点検項目

- 点検基準（テンプレート）を作成し、設備に割り当てる。設備固有の基準も作れる
- 点検項目: 表示順、項目名、判定基準、必須、対象外を許可するか
- **基準は版で管理**する。変更すると新しい版になり、過去の点検は当時の版のまま表示される。変更理由・変更者・日時を残す

### F-10 ユーザー管理・システム設定

- TENQ ロール・所属工場・TENQ 内利用停止の設定（アカウントの作成・削除は Space.app 側）
- システム設定: 保存期間、危険度「高」の案内文、点検中のまま放置された点検の扱い、写真の上限、出力できるロール 等

### F-11 監査ログ・記録管理（§6 指示）

- 作成者・作成日時、更新者・更新日時をすべての記録に保存
- 確定した点検記録は上書きしない。訂正は「新しい版」として追加し、元の記録・訂正理由・訂正者を残す
- 一般社員は確定記録を訂正・削除できない
- 監査ログは追記専用（API に更新・削除の口を作らず、DB トリガーでも更新・削除を拒否する）
- 保存期間を設定でき、期間を過ぎた記録を一覧できる。**自動削除はしない**（削除は承認手続きを決めてから。§10 Q-8）

- スマホ: 同モックの共通画面（QR を読む → その設備の点検表 → 項目ごとのカードに「正常 / 異常 / 対象外」ボタン → 完了）。最初のモック `_mock-proposals.html` の A 案「クリア・カード」と同じ形

## 6. 非機能要件

| 区分 | 要件 |
| --- | --- |
| 性能 | 点検画面の表示 2 秒以内（社内 Wi-Fi）、API 応答 p95 500ms 以内（外部認証の待ちを除く） |
| 可用性 | 業務時間帯に利用できること。Cloudflare / Railway の障害時は紙の点検表で代替する手順を用意（operations.md） |
| 容量 | Worker 非圧縮バンドル 1MiB 以内（社内目標）。D1・R2 の使用量を月次で確認 |
| 保守 | 依存パッケージは必要最小限。DB 変更はマイグレーションファイルのみ |
| ブラウザ | iOS Safari 17 以降、Android Chrome 最新、PC の Chrome / Edge 最新 |
| アクセシビリティ | 色だけで判定を区別しない（正常/異常は文字とアイコンも併記） |
| 時刻 | 保存は UTC、点検日・期限は工場のタイムゾーン（既定 Asia/Tokyo）で判定 |

## 7. スコープ外（初期）

- オフライン点検（電波のない場所での入力・後送信）
- 専用ネイティブアプリ、プッシュ通知、メール通知（Phase 2 で検討）
- 数値入力型の点検項目（温度・圧力などの計測値と閾値判定）— Phase 2 候補
- 予防保全計画・部品在庫・稼働率管理
- 電子署名（法的効力のある署名）

## 9. 品質管理担当者に確認してもらう事項

- 適用規格（ISO 9001 / 14001 / 45001 など）と、日常点検記録が該当する条項
- 記録の保存期間（設備台帳・点検記録・異常/是正記録それぞれ）
- 承認方法（工場長の画面上の承認で足りるか、押印・署名が別途必要か）
- 訂正のルール（誰が・いつまで・どんな理由なら訂正できるか）
- 紙の点検表からの移行時期と、並行運用期間の扱い
