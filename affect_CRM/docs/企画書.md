## 1. Context（背景と目的）

### なぜ作るのか

サーフショップ affect では、来店客との接点が「スタッフの記憶」と「紙・個別のメモ」に散っており、次の問いに答えられない状態にある。

- 昨日来た人は誰で、何を見に来たのか
- なぜ買わなかったのか。その人にいつ、何を提案すべきか
- スクールに来た人が、その後ボードやウェットを買っているのか
- Instagram を見て来た客と、紹介で来た客では、どちらが購入に至るのか

### 何を作るのか

単なる顧客名簿ではなく、**顧客との接点を時系列で蓄積し、次の一手を出せる基幹システム**を作る。中心にあるのは次の流れである。

```
来店 → 接客 → 興味 → 購入 / 未購入 → フォロー → スクール → 再来店
```

### 最終ゴール

1. **入力が続くこと** — 店舗スタッフがスマホで、接客の合間に30秒で記録を残せる
2. **未購入が資産になること** — 買わなかった理由が必ず残り、後日の提案につながる
3. **予約のマスターになること** — CRM で管理した枠がそのままホームページの予約枠になる
4. **数字で判断できること** — 来店経路別・年代別の購入率まで分析でき、CSV で外部にも出せる

「動くこと」ではなく「**実際の店舗スタッフが毎日使い続けられること**」を全ての判断基準とする。

## 3. 技術構成と推奨ディレクトリ構成（⑥）

### 3-1. 技術選定

| 項目 | 採用 | 理由 |
|---|---|---|
| フレームワーク | **Next.js 16 (App Router)** | 指示書の指定。管理画面と公開予約ページを 1 アプリで賄える |
| 言語 | **TypeScript** | 指示書の指定 |
| CSS | **Tailwind CSS 4** | 指示書の指定。TimeCalc と同バージョン |
| ORM | **Prisma 6.19** | 指示書の指定 |
| DB | **Cloudflare D1 (SQLite)** | ★下記参照 |
| 認証 | **自前実装（jose の JWT + bcryptjs）** | TimeCalc と同方式。NextAuth は Workers 環境で構成が重くなるため見送り |
| トークン保持 | **sessionStorage + Bearer ヘッダー** | ★★下記参照 |
| データ取得 | **クライアント fetch + Route Handler**（管理画面）| ★★下記参照 |
| デプロイ | **Cloudflare Workers（OpenNext 1.20 経由）** | 指示書の指定 |
| バリデーション | **zod** | 入力値検証をサーバー側で統一 |
| グラフ | **軽量ライブラリ or 自前 SVG**（Phase 4 で確定） | バンドルサイズを Workers の制限内に保つ |

**★ DB を PostgreSQL ではなく D1 にする理由（指示書からの逸脱点・要確認事項）**

指示書 3 章では PostgreSQL が指定されているが、以下の理由から Cloudflare D1（SQLite）を推奨する。

1. Cloudflare Workers へのデプロイが前提であり、D1 なら同一プラットフォーム内で完結する（外部 DB への接続設定・接続数制限・レイテンシの問題が発生しない）
2. 同モノレポの TimeCalc がこの構成で本番稼働しており、デプロイ・マイグレーションの知見がそのまま使える
3. 店舗 1 店・顧客数千件規模のデータ量では SQLite で性能上の問題は出ない
4. 追加の月額コストが発生しない

**移行余地の確保**: Prisma を使うため、将来 PostgreSQL へ移す場合も `datasource provider` の差し替えで対応できる設計にする。ただし D1 固有の制約は 4-6 節に記載のとおり設計へ織り込む。

**★★ 認証を Cookie ではなく sessionStorage + Bearer にする理由**

TimeCalc は当初 Server Component + Server Action で作られたが、**現在は全面的に CSR（クライアント fetch + Route Handler）へ移行済み**である。理由は「タブごとに別アカウントでログインできる状態を作るため」で、Server Component / Server Action は Cookie 認証を前提としており、sessionStorage のトークンが届かないためこの組み合わせは成立しない。

affect CRM でもこの方式を採用する。得られる利点は次の 2 点。

1. **管理者とスタッフを別タブに並べて動作確認できる**（権限まわりの検証コストが劇的に下がる）
2. CSRF 対策が構造的に不要になる（Cookie を自動送信しないため）

**ただし公開予約ページ `(public)/reserve` は例外**とし、こちらは認証不要なので Server Component でのデータ取得を許す。初期表示が速く、SEO 上も有利で、Bearer トークンを持たない画面なので上記の制約を受けないため。

**★★ データ取得を Route Handler に統一する理由**: 上記の帰結として、管理画面のデータ取得は `"use client"` なページから `apiFetch()` で `/api/*` を叩く形に統一する。Server Action は使わない。TimeCalc で実証済みの構成であり、パターンを混在させないことでコードの読み方が 1 つに定まる。

### 3-2. 運用コスト（0 円運用の設計）

**月額 0 円で運用する**ことを設計上の制約とする。Cloudflare の無料枠で完結させ、有料サービスを構成に入れない。

| 項目 | 使うもの | 無料枠 | affect の想定使用量 |
|---|---|---|---|
| アプリ実行 | Cloudflare Workers (Free) | 10 万リクエスト/日 | スタッフ数名 + Web 予約。1 日数百〜数千程度で**十分収まる** |
| データベース | Cloudflare D1 (Free) | ストレージ 5GB / 読み取り 500 万行・書き込み 10 万行 per 日 | 顧客数千件・来店数万件でも**桁違いに余裕がある** |
| ドメイン | `*.workers.dev` のサブドメイン | 無料 | 独自ドメインを使う場合のみドメイン代が発生（年 1,000〜2,000 円程度）|
| 画像保存（将来） | Cloudflare R2 | 10GB | 現時点では使わない |

**0 円を守るための設計ルール**

- 認証に外部 SaaS（Auth0 等）を使わない → 自前の JWT 実装（3-1 で決定済み）
- メール送信サービスを構成に入れない → 予約完了メールが必要になった時点で、無料枠のある送信サービスを別途検討する（Phase 2 以降の判断事項）
- グラフは**外部 API を使わず**クライアント側で描画する（軽量 OSS ライブラリまたは自前 SVG）
- 監視・エラー追跡の SaaS を入れない → Cloudflare のダッシュボードと `wrangler tail` で足りる
- AI 分析機能（将来構想）は、無料枠のあるモデルを使うか、有料化の判断を別途行う

**注意点**: D1 の無料枠は「書き込み 10 万行/日」がボトルネックになり得るが、店舗 1 店の来店・購入記録では 1 日数百行に届かないため問題にならない。逆に**バッチ処理で全顧客の集計値を毎日書き直すような実装をすると無料枠を圧迫する**ため、4-4 で決めたとおり集計は都度算出を基本とする。

**設計方針**

- 管理画面 `(app)` と公開ページ `(public)` を Route Group で分離する。認証・レイアウト・デザインの要件が根本的に違う（業務効率優先 vs ブランドイメージ優先）ため、レイアウトを共有しない

- API 側は `route.ts` / `[id]/route.ts` / **`_shared.ts`**（複数ルートが共有するパース・バリデーション。`_` 始まりはルートにならない）で構成する
- UI は Button コンポーネントを作らず、**クラス文字列の定数**（`buttonPrimaryClass` 等）を export する。`<button>` にも `<Link>` にも同じ見た目を適用でき、取り回しが良いため

### 4-3. 重複顧客防止（指示書 33 章）

1. **正規化列で検知**: `phoneDigits`（ハイフン等を除去した数字のみ）、`emailLower` にインデックスを張る
2. **unique 制約はかけない**: 電話番号を持たない顧客、家族で同一番号を共有するケースが実在するため。制約で弾くと登録できなくなる
3. **登録時にサジェスト**: スタッフ登録・Web 予約の両方で、電話/メール一致の既存顧客を候補として提示する
4. **自動統合はしない**: 電話・メールが完全一致し、かつ氏名も一致する場合のみ既存顧客に自動紐付け。それ以外は「候補あり」としてスタッフに判断させる（指示書の要求どおり、断定できない場合は統合しない）
5. 統合機能（マージ）は Phase 3 以降で、管理者権限に限定して実装する

### 4-4. 集計値の扱い

`visitCount` / `purchaseTotal` などの集計値は、**都度計算を基本としつつ、顧客一覧の絞り込み・並べ替えに使う指標だけ非正規化列にキャッシュ**する。

- 理由: 「来店回数が多い順」「累計購入金額が多い順」で一覧をソートし、「来店回数 3 回以上」で絞り込む要件があるため。集計値を持たないと、この検索がサブクエリだらけになり顧客数の増加とともに重くなる
- 更新: 来店・購入・スクール参加の登録／更新／削除時に、同じ処理内でキャッシュ列を再計算する
- **正はあくまで履歴テーブル**: キャッシュ列は検索・ソートのための補助であり、金額の正しさは常に `Purchase` の合計が決める。カルテに表示する数値も履歴から算出した値を使う
- 整合性の担保: 集計値を全顧客分作り直す再計算処理（管理者向け）を用意し、ズレが疑われたら実行できるようにする

> 補足: 同構成の TimeCalc は「計算結果を DB に保存せず、生データと設定から毎回計算する」方針を採っており、affect CRM もこれを基本とする。集計キャッシュ列は**顧客一覧の検索・ソートという明確な要件のためだけの例外**と位置づけ、他の指標（分析画面の数値など）は都度算出する。

### 4-5. データ削除の方針

- 顧客: **論理削除**（`deletedAt`）。管理者のみ実行可。履歴データは残す
- 来店・購入・予約: 誤登録の訂正が現場で必ず発生するため物理削除を許可するが、**管理者のみ**とし、スタッフは編集までとする
- マスタ類（タグ・選択肢・商品・コース）: 削除ではなく `isActive = false` による無効化を基本とする。過去データの表示が壊れないため

### 4-6. D1 (SQLite) 固有の制約と対応

| 制約 | 対応 |
|---|---|
| Prisma の `enum` が使えない | `String` + `src/lib/constants.ts` の定数（`as const` タプル → union 型）と zod で値を担保する |
| **Cloudflare Workers は常に UTC で動く**（`TZ` 環境変数が効かない） | ★最重要。`src/lib/utils/time.ts` に JST 変換関数を**最初に**用意し、「今日の来店」「今月の売上」の境界計算を必ずそこに集約する。日付を扱うコードを 1 行も書く前に整備する |
| 全文検索・`mode: "insensitive"` が使えない | 氏名検索は `nameKana` と小文字正規化列で対応する |
| トランザクションが限定的 | 予約の残席チェックは「確定直前に再チェック」を必ず入れる（4-8） |
| 金額の小数型を避ける | 金額はすべて `Int`（円）で保持する |

**UTC 問題の重要性**: 同構成の TimeCalc が実際にこれを踏み、日付のズレを修正するコミットが入っている。来店日・予約日・売上集計と、日付が意味を持つデータばかりを扱う affect CRM では**確実に踏む**。「今日の来店者数」が UTC 基準で数えられると、日本時間の朝 9 時より前の来店が前日に計上されるといった形で、静かに数字が狂う。

### 4-7. お名前が分からないお客様（匿名来店）の扱い ★重要

サーフショップでは「ふらっと入って、見て、帰る」お客様が日常的に発生する。**その方たちを記録から落とすと、来店数も購入率も実態とずれる**。よって「顧客に紐づかない来店」を正式にサポートする。

**設計**

1. `Visit.customerId` を**任意（nullable）**にする。顧客レコードを作らずに来店だけ記録できる
2. 匿名時は `guestAgeGroup` / `guestGender` / `partySize` を選択式で記録する（**2 タップで済む**）
3. 未購入理由も通常どおり記録する（匿名では「情報収集」「相談のみ」「見るだけ」が中心になる想定）
4. **後から顧客に紐付けられる**。来店詳細画面で顧客を指定すると、その来店が顧客の履歴に加わり、集計キャッシュも再計算される
5. 購入・予約・スクール参加は**顧客必須のまま**（履歴を人に紐づける必要があるため）。ただし匿名のまま売上だけ記録する経路は残す

**「仮顧客」レコードを作らない理由**: `name = "（名前未確認）"` のような顧客を量産すると、顧客一覧が実在しない人で埋まり、顧客数・リピート率といった指標が壊れる。**顧客と来店は別の概念**なので、来店だけを記録できる形にする方が正しい。

**分析での扱い**

| 指標 | 匿名来店の扱い |
|---|---|
| 来店数・購入率・未購入理由 | **含める**（実態を反映するため） |
| 年代別・性別・来店経路別 | **含める**（`guestAgeGroup` / `guestGender` を使う。顧客紐付きなら `Customer` 側の値を使う） |
| 新規顧客数・リピート率・LTV | **含めない**（顧客レコードがないため） |
| **お名前を伺えた率** | 新指標。`顧客紐付きの来店 ÷ 全来店`。**接客で声をかけられているかの指標**になり、低ければ改善点として見える |

**個人情報の扱い**: 匿名記録でも個人情報として扱う。識別メモは「赤いキャップ」程度に留め、容姿の詳細な記述は運用ルールとして禁止する。

### 4-8. 予約の同時実行（Web 予約の要注意点）

複数の来訪者が同時に最後の 1 枠を予約するケースが起こり得る。D1 では厳密なロックが取りにくいため、以下で対応する。

1. 予約作成時、同一処理内で「有効な予約（`TENTATIVE`/`CONFIRMED`/`ATTENDED`）の人数合計」を再集計する
2. 定員を超える場合はエラーを返し、「満席になりました」と表示して枠一覧に戻す
3. Web 予約の初期ステータスは **`TENTATIVE`（仮予約）** とし、店舗側が確定する運用にすることで、万一の超過も人間が吸収できるようにする（この運用可否は要確認事項）

## 6. UI/UX 設計方針

### 6-1. デザイン

- **トーン**: シンプル・清潔・サーフショップらしい。派手な管理画面にしない
- **カラー**: ベース = 白／オフホワイト、メイン = ディープネイビー〜オーシャンブルー、アクセント = サンドベージュ。ステータス色（成功/警告/危険）は最小限
- **余白**: 十分に取る。情報密度より可読性を優先
- **公開予約ページ**: 管理画面とはトーンを変え、写真と余白を活かしたブランド重視のデザインにする

### 6-2. レスポンシブ

| 画面幅 | ナビゲーション | 一覧表示 |
|---|---|---|
| PC (≥1024px) | 左サイドバー固定 | テーブル |
| タブレット (768–1023px) | 折りたたみサイドバー | テーブル（列を絞る） |
| スマホ (<768px) | **下部固定ナビ + スライドメニュー** | **カード表示** |

### 6-3. スマホ最適化（指示書 27・28 章）

- 下部固定ナビ: **［ホーム］［顧客］［＋来店］［予約］［メニュー］** の 5 つ。中央の「＋来店」を一番大きく、親指が届く位置に配置
- タップ領域は最低 44×44px を確保
- フォームは 1 カラム、下部に**固定の保存バー**
- 横スクロールを発生させない（テーブルはカードへ変換）
- キーボード入力を減らす: 選択式・トグル・チップ選択を多用し、日時は既定値を入れておく
- 数値・電話・メールは適切な `inputMode` を指定してキーボードを最適化

### 6-4. UX ルール

- **用語を統一**: 「保存」「登録」「編集」「削除」「キャンセル」の意味を全画面で固定する
- **エラーは具体的に**: 「入力してください」ではなく「**氏名を入力してください**」。どの項目かを必ず明示する
- 破壊的操作（削除）は必ず確認ダイアログを挟む
- 保存後はトーストで結果を明示し、直前の一覧位置に戻す（スタッフの連続入力を止めない）

## 7. 権限とセキュリティ

### 7-1. 権限（指示書 34 章）

| 機能 | 管理者(ADMIN) | スタッフ(STAFF) |
|---|---|---|
| 顧客・来店・購入・予約・フォローの閲覧／登録／編集 | ○ | ○ |
| 顧客の削除、各種データの削除 | ○ | × |
| 商品・コース・タグ・選択肢マスタの編集 | ○ | × |
| スタッフ管理（追加・権限変更・無効化） | ○ | × |
| 設定変更 | ○ | × |
| 分析・CSV 出力 | ○ | ○（顧客個人情報を含む出力は管理者のみ） |

将来の役割追加（閲覧のみのアルバイト等）に備え、権限判定はロール文字列の直接比較ではなく `can(user, "customer.delete")` 形式の判定関数に集約する。

### 7-2. セキュリティ（指示書 35 章）

| 項目 | 対策 |
|---|---|
| 認証 | パスワードは bcrypt でハッシュ化。JWT（HS256・有効期限つき）を発行し、署名鍵は Cloudflare のシークレットで管理する。**ログイン失敗時にユーザー不存在とパスワード不一致でメッセージを変えない**（アカウント列挙対策） |
| 認可 | **すべての Route Handler の先頭で `requireApiUser()` / `requireApiPermission()` を必ず通す**。画面のボタンを隠すだけの制御はしない（API を直接叩かれたら素通りになるため） |
| API アクセス制御 | 公開エンドポイントは `/api/public/*` に限定し、それ以外は認証必須をデフォルトにする |
| 入力値検証 | zod スキーマをサーバー側で必ず実行（クライアント検証はあくまで UX 向上のため） |
| SQL インジェクション | Prisma のクエリビルダのみを使用。生 SQL は原則禁止、使う場合もパラメータ化を徹底 |
| XSS | React の自動エスケープに委ね、`dangerouslySetInnerHTML` を使わない |
| CSRF | **該当なし**。Bearer トークン方式のため、ブラウザが認証情報を自動送信しない |
| シークレット管理 | **`.env` に本番用の値を置かない**。OpenNext は `.env` の内容を Worker のバンドルに焼き込むため。本番の署名鍵は `wrangler secret put` で設定する |
| 個人情報のログ | **氏名・電話番号・メール・住所をログに出力しない**。エラーログには顧客 ID のみ記録する |
| 公開予約の悪用対策 | `/api/public/*` にレート制限（IP 単位）を設け、大量の仮予約作成を防ぐ |

## 10. 検証方法

各 Phase で以下を必ず実施する。

1. **ローカル起動**: `npm run dev` で開発サーバーを起動し、実際にブラウザで操作する
2. **スマホ幅の確認**: DevTools のデバイスエミュレーション（375px 幅）で、下部ナビ・カード表示・固定保存バー・横スクロールの有無を確認する
3. **主要フローの通し確認**（Phase 1）:
   - ログイン → 顧客を新規登録 → クイック来店登録（未購入・理由「検討中」）→ 顧客カルテに来店履歴が出る → 購入を登録 → 累計購入金額と来店回数が更新される
   - 同じ電話番号で顧客を登録しようとすると重複候補が提示される
   - スタッフ権限でログインし、削除ボタンが機能しない（403 が返る）ことを確認する
4. **エラー系**: 必須項目を空で保存 →「氏名を入力してください」のように項目名付きで表示されること
5. **デプロイ確認**: Cloudflare へのデプロイは**手動コマンドの実行が必要**（push だけでは本番反映されない）。反映確認は HTTP 200 ではなく、画面上の固有文字列で判定する

## 12. 技術基盤の詳細（実装時の必須事項）

同一構成で本番稼働している TimeCalc の実装から抽出した、**踏むと確実に時間を失う落とし穴**と対処。Phase 1 の着手時にこれを前提として構築する。

### 12-1. 環境構築

| 項目 | 内容 |
|---|---|
| バージョン | Next.js 16.2 / React 19.2（`^` なしでピン留め）/ Tailwind 4.3 / Prisma 6.19 / OpenNext 1.20 / Wrangler 4.11 |
| `next.config.ts` | export のあとに `initOpenNextCloudflareForDev()` を呼ぶ。**これがないとローカル開発で DB に一切つながらない** |
| `wrangler.jsonc` | `compatibility_flags: ["nodejs_compat"]` が**必須**（bcryptjs が動かないため） |
| Tailwind 4 | `tailwind.config.ts` は**作らない**。`globals.css` に `@import "tailwindcss"` と `@theme inline` でトークンを定義する（v3 とは書き方が根本的に違う） |
| Prisma generator | `provider = "prisma-client"`（`-js` ではない）+ `runtime = "cloudflare"` + `output` 指定。旧 generator では WASM がバンドルから漏れて本番で動かない |
| import 元 | Prisma の型・クライアントは `@/generated/prisma/client` から import する。`@prisma/client` から import すると本番で壊れる |

### 12-2. D1 接続の最重要事項

PrismaClient はリクエストごとに Cloudflare のバインディングから生成する必要がある。このとき**キャッシュのキーに環境オブジェクトを使ってはいけない**。環境オブジェクトはリクエストをまたいで共有されるため、PrismaClient が使い回されて**応答がハングし 500 になる**（TimeCalc が実際に踏み、修正済み）。リクエストごとに新規生成されるコンテキストの戻り値そのものをキーにする。

この実装は TimeCalc の `src/lib/db.ts` に理由のコメント込みで残っているため、**丸ごと流用する**。

### 12-3. マイグレーション

`prisma migrate deploy` は D1 に対して使えない。次の流れになる。

1. `prisma/schema.prisma` を書く
2. `prisma migrate diff` で SQL を生成し `migrations/000N_xxx.sql` に保存する
3. `wrangler d1 execute affect-crm --local --file ...` でローカル適用 → 確認
4. `wrangler d1 execute affect-crm --remote --file ...` で本番適用

各 SQL ファイルの冒頭に**実行コマンドをコメントで残す**（TimeCalc の運用。これがないと後から再現できなくなる）。

### 12-4. デプロイ

- **CI/CD はない。`git push` しても本番は一切変わらない。** 本番反映は `npm run cf:deploy` を手で実行するのが唯一の経路
- **DB のスキーマ変更はデプロイに含まれない。** 順序は「D1 に SQL を適用 → `cf:deploy`」
- 反映確認は HTTP 200 ではなく、**画面上の固有の文字列**で判定する
- デプロイ前に `npm run cf:preview` でローカルの Worker 実体を確認する

### 12-5. Next.js 16 の変更点（実装時に必ず当たるもの）

1. `params` / `searchParams` / `cookies()` / `headers()` は **Promise**。Route Handler では `const { id } = await params;`
2. `middleware.ts` は `proxy.ts` にリネームされた。→ **そもそも使わない**（認証は Route Handler のガードで行う）
3. Turbopack がデフォルト。webpack 設定を書くとビルドが失敗する
4. `next lint` は削除された。`eslint` を直接実行する
5. ESLint は Flat Config

Next.js 16 は学習データと差異が大きいため、**実装時は `node_modules/next/dist/docs/` の該当ガイドを読んでから書く**。

### 12-6. スマホ UI の実装上の注意

- 入力欄のフォントは **16px 以上**（`text-base`）。これより小さいと iOS Safari がフォーカス時に勝手にズームする。PC では `sm:text-sm` で戻す
- 入力欄・ボタンの高さは `min-h-11`（44px）を基準にし、PC で `sm:min-h-10` に縮める
- Tailwind 4 の `!important` は**後置き**（`p-0!`）。v3 の `!p-0` は効かない

### 12-7. 安定性（Workers 特有）

Cloudflare Workers は散発的に応答を返さず 500 になることがある。TimeCalc では次の多層防御で実用上の問題を解消している。affect CRM でも共通の fetch ラッパーに最初から入れる。

- **GET のみ**自動リトライ（0.7 秒・2 秒 空けて 2 回まで）。POST は二重登録を防ぐため対象外にする
- 再取得に失敗しても、**画面に出ている内容を消さない**（スタッフの作業を止めないため）
- 401 を受けたらトークンを破棄してログイン画面へ戻す
